# Report page conventions

This repo (`coldnew/stock`) publishes standalone, self-contained HTML
investment-analysis reports under `reports/`, plus a landing `index.html`,
`sitemap.xml`, and `robots.txt` at the repo root. Every report is a single
`.html` file with everything inlined (CSS in `<style>`, JS in one `<script>`
before `</body>`) — no build step, no bundler, no shared external asset
files except the CDN-hosted font and third-party ad/analytics scripts.

Assumed hosting: **`https://coldnew.github.io/stock/`** — a GitHub Pages
project site for this repo, sharing the top-level domain with the user's
blog (`coldnew.github.io`). This is baked into every canonical/OG/sitemap
URL. GitHub Pages needs to actually be enabled on this repo for it to
resolve — that hasn't been confirmed done. If the real path ever turns out
different, every `https://coldnew.github.io/stock/...` URL across
`reports/*.html`, `index.html`, `sitemap.xml`, and `robots.txt` needs a
find-and-replace.

## Design system

Originally generated by the Kami skill (`generator: Kami` in each report's
`<meta>`), a "parchment" design system meant for print/PDF export
(`@page` rules still present) but now used primarily on-screen. CSS custom
properties on `:root`:

```
--parchment (page bg) --ivory (card/section bg) --near-black (text)
--dark-warm --olive --stone (secondary text) --brand (#1B365D navy, accent)
--border --border-soft --tag-bg --positive --negative
--serif: "TsangerJinKai02", "Source Han Serif TC", ... Georgia, serif
```

Dark mode: `[data-theme="dark"]` redefines the same tokens (see any
report's `<style>` for the exact dark palette). Everything downstream
(headings, tables, callouts, risk grid, ad slots, TOC, tooltips) is styled
purely off these variables, so dark mode support is automatic for anything
new as long as it uses `var(--...)` instead of hardcoded colors. The
**inline SVG charts** are the one exception — their `fill`/`stroke` values
are hardcoded hex (e.g. `#f5f4ed`, `#1B365D`), not CSS vars, so chart
backgrounds stay parchment-colored even in dark mode. That's intentional:
charts read as light "cards" floating on the dark page rather than being
re-themed, since re-deriving every chart's pixel-positioned label/gridline
colors per-theme isn't worth the risk of breaking layout.

## Typography scale

Base body text is **12pt** (~16px), matching the blog's default article
size — bumped up from the original Kami template's 10pt because it read as
too small on screen. Every other CSS font-size in a report is that same
10pt-era value scaled by **1.2×** and rounded to the nearest 0.5pt (e.g.
9pt→11pt, 16pt→19pt, 24pt→29pt) — this preserves the original relative
type hierarchy. Prose line-height (`body`, `p`, `ul`/`ol`, `.callout`) is
**1.65** (up from 1.5), matching the blog's looser reading rhythm; denser
UI bits (compact tables, tooltips, TOC) were deliberately left tighter.

**In-chart SVG text was NOT scaled** — those are pixel-positioned
annotations baked into each chart's layout; scaling them blind risks
overlapping labels. If chart text ever needs to be bigger, that requires
regenerating the chart's coordinates, not a CSS tweak.

If you add new CSS to a report, size it in this same already-scaled range
(body text 12pt, secondary/label text ~10-11.5pt, headings 15.5-19pt) —
don't copy a raw value from the original Kami template or from an older
draft of this repo without scaling it.

## The interactive layer

Every report has one inline `<script>` before `</body>` (identical logic
copy-pasted across reports — no shared JS file) doing five things:

1. **Theme toggle** — top-right circular button. First visit follows
   `prefers-color-scheme`; once clicked, the choice is saved to
   `localStorage` under the key **`report-theme`** and overrides system
   preference from then on. `index.html` uses the **same key**, so the
   preference is shared site-wide (same origin) across the index and every
   report — keep reusing `report-theme` in any new page, don't invent a
   per-page key.
2. **Sticky TOC + scrollspy** — auto-built from every `<h2>` in the page,
   fixed on the **right** side (`right: 16px`, width `170px`, vertically
   centered), hidden under 1180px viewport width. Highlights the section in
   view via `IntersectionObserver` (guarded with
   `if (window.IntersectionObserver)` so its absence can't take down the
   rest of the script — this guard is load-bearing, don't remove it). Plus a
   back-to-top button, bottom-right.

   The hide breakpoint must be derived from the actual geometry, not picked
   round: body content is capped at 210mm (~793.7px) and centered via
   `margin: 0 auto`, so the free margin on each side at viewport width `v` is
   `(v - 793.7) / 2`; the TOC needs that margin to be at least its own width
   plus its right offset plus a small buffer. The original breakpoint
   (1300px, with `right: 2vw` and `width: 190px`) was picked without doing
   this math and hid the TOC on very common viewport widths — 1280px in
   particular (the default logical resolution of a MacBook Air), where the
   TOC would actually have fit — which is why the user hit a real "TOC just
   isn't there" bug. Recompute the minimum safe breakpoint whenever the TOC's
   width/offset changes.
3. **Collapsible sections** — `buildSections()` walks `body`'s direct
   children; every `<h2>` becomes a click-to-collapse toggle, and every
   sibling up to the next `<h2>` gets swept into that heading's
   `.section-body` wrapper. **Elements that must stay visible regardless of
   collapse state are excluded from this sweep** via an explicit class
   check:
   ```js
   } else if (el.classList && (el.classList.contains('report-footer') || el.classList.contains('ad-slot') || el.classList.contains('related-report'))) {
   ```
   Currently excluded: `.report-footer`, `.ad-slot` (see the `add-ads`
   skill), `.related-report`. `.breadcrumb` doesn't need to be in this list
   — it's always placed before the first `<h2>`, where `current` is `null`
   from the start. `.related-report` **does** need to be in the list: it was
   originally assumed safe because it sits right after the bottom `.ad-slot`
   (which resets `current` to `null`), but `BTCI.html` was authored with no
   ad slots at all, so `.related-report` landed directly after the last
   section's content with nothing resetting `current` first — it silently
   got swept into that section and vanished on collapse. Caught by the
   jsdom smoke test's `relatedReportOutsideSection` check, not by eye. Moral:
   don't assume a "safe by position" element stays safe once a sibling
   assumption (like "there's always an ad-slot before this") stops holding.
   If you ever add a new always-visible element in the *middle* of the
   content flow (not at one of those natural boundaries), add its class to
   this exclusion check — otherwise collapsing that
   section hides it.
4. **Chart tooltips + legend toggle** — a generic engine, not hand-tuned
   per chart. It reads each chart's own axis gridlines/tick labels to
   build a value scale (works because every chart follows the same
   authoring convention: `#e8e7e1` horizontal gridlines paired with
   `text-anchor="end"` value labels on the left, `text-anchor="middle"`
   date/category labels along the bottom), then shows a crosshair +
   tooltip on hover and lets you click a legend swatch to hide/show that
   series everywhere it appears (by matching `stroke`/`fill` color, not by
   an explicit id). **This means any new chart added to a report must
   follow that same SVG authoring convention** (gridline color, text
   anchors, legend row below the x-axis labels) for hover/toggle to work
   automatically — it isn't wired up per-chart.
5. **Candlestick tooltips** — a separate, explicit-data engine, not
   geometry-detection like #4. Every report has one "近期股價走勢" chart
   (~50 trading days) built from real OHLC data fetched live (see below),
   generated by a small Python script rather than hand-drawn, because
   hand-computing pixel math for 50 bars across 4 tickers invites
   arithmetic errors. Each bar is a `<g class="candle" data-date="..."
   data-o=".." data-h=".." data-l=".." data-c="..">` wrapping its wick
   `<line>` and body `<rect>` — nesting inside `<g>` is what keeps these
   marks invisible to the generic line/bar detectors in #4 (which only
   scan `svg.children`, i.e. direct children, not nested ones), so the two
   engines never collide on the same chart. `setupCandlestickTooltip()`
   queries `svg.querySelectorAll('g.candle')` (a deep query, unlike the
   direct-children scan) and reads the `data-*` attributes straight into
   the tooltip — no pixel-to-value inversion needed, unlike #4. Up/down
   colors were tried once as `--brand`/`--negative` (navy/grey, matching
   `.price-change`) and rejected — too subtle for a candlestick chart,
   which needs strong two-color contrast to read at a glance. Now fixed
   hex `#C23B32` (red) = up, `#3A7A4E` (green) = down — and since these
   reports are explicitly for Taiwanese investors, that's the **Taiwan/
   Asia convention** (red = 漲/up, green = 跌/down), the opposite of the
   US/Western green-up/red-down. Don't swap it to Western convention
   without checking with the user first — it was a deliberate audience
   call, not a default. Both colors are fixed hex values directly in the
   SVG (not CSS vars), matching how every other chart in these reports
   already ignores dark-mode theming — see the design-system section
   above for why. When adding a new report, fetch real recent daily OHLC for
   its ticker (don't fabricate it) and regenerate with the same approach;
   the price data should also cross-check against the report's own header
   price/date for the most recent bar.

   **Never hand-type the generated `<g class="candle">` coordinates into
   the report file.** When SPYI was first authored, the candlestick SVG
   was typed out by hand while composing the report instead of pasting the
   actual Python script's output — every coordinate came out wrong (a diff
   against the real generated file showed every single `<line>`/`<rect>`
   mismatched), and one candle even ended up with a stray navy `#1B365D`
   stroke that isn't part of the red/green up/down palette at all. Run the
   generator, then copy its output file's contents into the report
   verbatim (Read the generated file, paste that exact text) — never
   reconstruct it from memory or "close enough" while writing the
   surrounding HTML.

If you regenerate or hand-roll this script block for a new report, copy it
verbatim from an existing report rather than rewriting it — it's had a few
rounds of correctness fixes (the `IntersectionObserver` guard, the
`ad-slot` exclusion, the y-axis baseline calculation for x-tick detection)
that are easy to reintroduce bugs into if rewritten from a description.

## SEO setup

Every report (`reports/*.html`) and `index.html` carries:

- `<meta name="viewport">`, `<title>`, `description`, `keywords`
- `<link rel="canonical">` — full `https://coldnew.github.io/stock/...` URL
- `<meta name="robots" content="index, follow">`
- Open Graph (`og:type`, `og:url`, `og:title`, `og:description`) + Twitter
  card (`summary`) — **no `og:image`/`twitter:image` yet**, there's no
  image-generation tooling available to produce one; this is a known,
  intentionally-flagged gap, not an oversight to silently repeat
- `<link rel="sitemap" href="https://coldnew.github.io/stock/sitemap.xml">`
- Google Analytics — **reuses the blog's measurement ID `G-2SXWWHGFPN`**
  (same `gtag.js` snippet as `src/components/BaseHead.astro` in the blog
  repo), meaning report traffic mixes into the same GA4 property as blog
  traffic rather than being tracked separately. That was a deliberate
  choice made once, not re-derived each time — if the user ever wants
  reports tracked separately, that needs an explicit new GA4 property/ID,
  don't assume it.
- `<script type="application/ld+json">` — `Article` schema on reports
  (headline/description/author/dates/mainEntityOfPage), `CollectionPage`
  with a `hasPart` array of `Article` entries on `index.html`
- Favicon — inline SVG data URI (brand-navy square, white uptrend line),
  no external asset file; reuse the same data URI across pages rather than
  designing a new one per report
- `<link rel="preconnect">` to `cdn.jsdelivr.net` and
  `www.googletagmanager.com`
- `font-display: swap;` on both `@font-face` rules
- A real `<h1>` — the report title (`.ticker-name`) is an `<h1>`, not a
  styled `<div>`. Keep it that way; don't regress to a div for a new report.
- `@media (max-width: 640px) { table, .kami-table { display: block;
  overflow-x: auto; white-space: nowrap; } }` so wide financial tables
  scroll instead of breaking mobile layout
- `.breadcrumb` (top, links to `../index.html`) and `.related-report`
  (bottom, links to *every other* report — a full mesh across all reports
  in `reports/`, not a single pick) for internal linking

`sitemap.xml` and `robots.txt` live at the repo root, not per-report.

## The ROC tax callout — conditional, not universal

Every income-fund report (OVL/QQQI/BTCI/GPIQ/SPYI/JEPI/JEPQ/QDVO — check
`ls reports/` for the current roster) has a `.callout` in its
"基本介紹" section explaining ROC (Return of Capital) as a US withholding-
tax angle for Taiwanese investors, plus a "配息時間表" distribution-date
table. **This only applies to securities that actually pay distributions.**
When TSLA (an individual stock, no dividend) was first generated by copying
the ETF template, the ROC callout got carried over verbatim and had to be
removed — even a version that correctly said "this doesn't apply here" was
still unwanted noise, not just inaccurate content. For a future non-paying
security (a growth stock, a fund that's never distributed, etc.), skip the
ROC callout and the distribution-date table entirely rather than including
a caveated version of either. For a security that *does* pay dividends but
isn't one of these covered-call/income funds, the underlying tax mechanism
(30% NRA withholding, ROC reducing cost basis, Taiwan's separate 基本所得額
reporting) is still accurate background — use judgment on whether that
specific security's distributions are ROC-heavy enough to be worth
mentioning, rather than pasting the callout by default.

### Strong ROC evidence (disclosed payout ratio) — metric badge + appendix

When a fund's own disclosed payout ratio is extreme enough to be direct
evidence of heavy ROC (currently: SPYI at 308.78%, QDVO at 300.52% — both
well over 100%, i.e. distributing several times realized gains), don't just
bury that inside the "基本介紹" callout prose. Surface it as its own **5th
metric card** in the header metrics bar (normally exactly 4:
費用率/殖利率/beta/AUM), value "幾乎全為 ROC" wrapped in
`<a href="#roc-note">`, label "配息組成（推估）". This is the concrete
"one field says the return is almost entirely ROC" pattern the user asked
for after seeing QDVO's callout — don't add this 5th card for funds whose
ROC evidence is only the generic tax-mechanism background, not a specific
disclosed number.

The full explanation (the standard "為什麼台灣投資人會關注...稅務優勢" text)
then moves out of the inline callout into its own **appendix `<h2>` section**
near the end of the report (after the analyst-box, before the closing
ad-slot), so it doesn't repeat the same wall of text inline. The inline
callout in "基本介紹" shrinks to 2-3 sentences citing the specific number,
ending with a link to the appendix (`<a href="#roc-note">附錄：ROC 稅務說明
→</a>`).

The appendix heading needs `data-anchor="roc-note"` — a real attribute,
not a convention-only comment. The shared interactive script's
`buildSections()` unconditionally does `el.id = 'section-' + counter` for
every `<h2>` in document order, which would stomp any hand-set `id` you put
directly on that heading. The script was extended with one line to check
first: `el.getAttribute('data-anchor') || ('section-' + counter)` — so
`data-anchor` on an `<h2>` gives it a stable, human-readable id that
survives regardless of how many other `<h2>`s exist or get added later,
while every other heading keeps the old positional `section-N` id
unchanged. This line needs to be identical across all reports (like the
rest of the shared script) even in reports that don't currently use
`data-anchor` — check `grep -n "getAttribute('data-anchor')" reports/*.html`
matches on all of them before treating the shared script as in sync.
Anchoring to the `<h2>` itself (not some inner span) matters: only the
`.section-body` gets `display:none` on collapse, never the heading, so a
link to the heading's id always scrolls correctly even if a reader has
collapsed that section — a link into the middle of the section body
wouldn't have that guarantee.

Because a 5th metric card makes the row less predictable in width, the
`.metrics`/`.metric` CSS carries `flex-wrap: wrap` and `flex: 1 1 110pt`
(rather than a bare `flex: 1`) so it degrades to wrapping instead of
squeezing or overflowing on narrow viewports — this is also shared CSS,
keep it identical across every report even though only SPYI/QDVO currently
use a 5th card.

## Checklist: adding a brand-new report

1. Author the report HTML using an existing report as the template — copy
   its `<style>` block and interactive `<script>` verbatim (see above for
   why), then swap in the new content.
2. Confirm SVG charts follow the gridline/legend authoring convention
   described above, or hover tooltips silently won't work for them.
3. Add all the SEO meta described above (canonical/OG/robots/JSON-LD/GA/
   favicon/preconnect/font-display), a real `<h1>`, and the mobile-table
   CSS.
4. Add `.breadcrumb` (top) and `.related-report` (bottom) — every report
   in `reports/` links to **every other** report (a full mesh, not a
   single pick), so add the new report's link to *all* existing reports'
   `.related-report` lists too, and give the new report links to all of
   them. Check the actual current file list (`ls reports/`) rather than
   trusting a hardcoded ticker list anywhere in this skill — it will go
   stale as reports are added.
5. Fetch real recent daily OHLC data for the ticker (last ~50 trading
   days; stockanalysis.com's `/etf/<ticker>/history/` or `/stocks/<ticker>/history/`
   page works well) — don't fabricate it — and generate a candlestick
   chart with the approach described above (small Python script, not
   hand-drawn — see the cautionary note above about SPYI's first draft
   hand-typing the coordinates and getting them wrong). Cross-check the
   most recent bar's close against the report's own header price for the
   same date before using either.
6. Add the same top/mid/bottom `.ad-slot` pattern — see the `add-ads`
   skill. The user has confirmed ads belong on every page by default; a new
   report should get them without needing to ask again, using the same
   codes already live elsewhere in the site.
7. Add a `.report-card` entry to `index.html`'s `<main class="report-list">`.
8. Add a `<url>` entry to `sitemap.xml` (`<loc>`, `<lastmod>` = today,
   reasonable `<changefreq>`/`<priority>` — see existing entries).
9. Verify with a quick headless smoke test (jsdom, or open in a browser)
   that: the script runs with no console errors, section count matches
   `<h2>` count, `.ad-slot`/`.breadcrumb`/`.related-report` aren't nested
   inside any `.section-body`, and there's exactly one `<h1>`.

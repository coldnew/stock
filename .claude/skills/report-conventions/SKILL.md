# Report page conventions

This repo (`coldnew/stock`) publishes standalone, self-contained HTML
investment-analysis reports under `reports/`, plus a landing `index.html`,
`sitemap.xml`, and `robots.txt` at the repo root. Every report is a single
`.html` file with everything inlined (CSS in `<style>`, JS in one `<script>`
before `</body>`) — no build step, no bundler, no shared external asset
files except the CDN-hosted font and third-party ad/analytics scripts.

Assumed hosting: **`https://coldnew.github.io/stock/`** — a GitHub Pages
project site for this repo, sharing the top-level domain with the user's
blog (`coldnew.github.io`). This is baked into every canonical/OG/sitemap
URL. GitHub Pages needs to actually be enabled on this repo for it to
resolve — that hasn't been confirmed done. If the real path ever turns out
different, every `https://coldnew.github.io/stock/...` URL across
`reports/*.html`, `index.html`, `sitemap.xml`, and `robots.txt` needs a
find-and-replace.

## Design system

Originally generated by the Kami skill (`generator: Kami` in each report's
`<meta>`), a "parchment" design system meant for print/PDF export
(`@page` rules still present) but now used primarily on-screen. CSS custom
properties on `:root`:

```
--parchment (page bg) --ivory (card/section bg) --near-black (text)
--dark-warm --olive --stone (secondary text) --brand (#1B365D navy, accent)
--border --border-soft --tag-bg --positive --negative
--serif: "TsangerJinKai02", "Source Han Serif TC", ... Georgia, serif
```

Dark mode: `[data-theme="dark"]` redefines the same tokens (see any
report's `<style>` for the exact dark palette). Everything downstream
(headings, tables, callouts, risk grid, ad slots, TOC, tooltips) is styled
purely off these variables, so dark mode support is automatic for anything
new as long as it uses `var(--...)` instead of hardcoded colors. The
**inline SVG charts** are the one exception — their `fill`/`stroke` values
are hardcoded hex (e.g. `#f5f4ed`, `#1B365D`), not CSS vars, so chart
backgrounds stay parchment-colored even in dark mode. That's intentional:
charts read as light "cards" floating on the dark page rather than being
re-themed, since re-deriving every chart's pixel-positioned label/gridline
colors per-theme isn't worth the risk of breaking layout.

## Typography scale

Base body text is **12pt** (~16px), matching the blog's default article
size — bumped up from the original Kami template's 10pt because it read as
too small on screen. Every other CSS font-size in a report is that same
10pt-era value scaled by **1.2×** and rounded to the nearest 0.5pt (e.g.
9pt→11pt, 16pt→19pt, 24pt→29pt) — this preserves the original relative
type hierarchy. Prose line-height (`body`, `p`, `ul`/`ol`, `.callout`) is
**1.65** (up from 1.5), matching the blog's looser reading rhythm; denser
UI bits (compact tables, tooltips, TOC) were deliberately left tighter.

**In-chart SVG text was NOT scaled** — those are pixel-positioned
annotations baked into each chart's layout; scaling them blind risks
overlapping labels. If chart text ever needs to be bigger, that requires
regenerating the chart's coordinates, not a CSS tweak.

If you add new CSS to a report, size it in this same already-scaled range
(body text 12pt, secondary/label text ~10-11.5pt, headings 15.5-19pt) —
don't copy a raw value from the original Kami template or from an older
draft of this repo without scaling it.

## The interactive layer

Every report has one inline `<script>` before `</body>` (identical logic
copy-pasted across reports — no shared JS file) doing four things:

1. **Theme toggle** — top-right circular button. First visit follows
   `prefers-color-scheme`; once clicked, the choice is saved to
   `localStorage` under the key **`report-theme`** and overrides system
   preference from then on. `index.html` uses the **same key**, so the
   preference is shared site-wide (same origin) across the index and every
   report — keep reusing `report-theme` in any new page, don't invent a
   per-page key.
2. **Sticky TOC + scrollspy** — auto-built from every `<h2>` in the page,
   fixed on the **right** side (`right: 2vw`, vertically centered), hidden
   under 1300px viewport width. Highlights the section in view via
   `IntersectionObserver` (guarded with `if (window.IntersectionObserver)`
   so its absence can't take down the rest of the script — this guard is
   load-bearing, don't remove it). Plus a back-to-top button, bottom-right.
3. **Collapsible sections** — `buildSections()` walks `body`'s direct
   children; every `<h2>` becomes a click-to-collapse toggle, and every
   sibling up to the next `<h2>` gets swept into that heading's
   `.section-body` wrapper. **Elements that must stay visible regardless of
   collapse state are excluded from this sweep** via an explicit class
   check:
   ```js
   } else if (el.classList && (el.classList.contains('report-footer') || el.classList.contains('ad-slot') || el.classList.contains('related-report'))) {
   ```
   Currently excluded: `.report-footer`, `.ad-slot` (see the `add-ads`
   skill), `.related-report`. `.breadcrumb` doesn't need to be in this list
   — it's always placed before the first `<h2>`, where `current` is `null`
   from the start. `.related-report` **does** need to be in the list: it was
   originally assumed safe because it sits right after the bottom `.ad-slot`
   (which resets `current` to `null`), but `BTCI.html` was authored with no
   ad slots at all, so `.related-report` landed directly after the last
   section's content with nothing resetting `current` first — it silently
   got swept into that section and vanished on collapse. Caught by the
   jsdom smoke test's `relatedReportOutsideSection` check, not by eye. Moral:
   don't assume a "safe by position" element stays safe once a sibling
   assumption (like "there's always an ad-slot before this") stops holding.
   If you ever add a new always-visible element in the *middle* of the
   content flow (not at one of those natural boundaries), add its class to
   this exclusion check — otherwise collapsing that
   section hides it.
4. **Chart tooltips + legend toggle** — a generic engine, not hand-tuned
   per chart. It reads each chart's own axis gridlines/tick labels to
   build a value scale (works because every chart follows the same
   authoring convention: `#e8e7e1` horizontal gridlines paired with
   `text-anchor="end"` value labels on the left, `text-anchor="middle"`
   date/category labels along the bottom), then shows a crosshair +
   tooltip on hover and lets you click a legend swatch to hide/show that
   series everywhere it appears (by matching `stroke`/`fill` color, not by
   an explicit id). **This means any new chart added to a report must
   follow that same SVG authoring convention** (gridline color, text
   anchors, legend row below the x-axis labels) for hover/toggle to work
   automatically — it isn't wired up per-chart.

If you regenerate or hand-roll this script block for a new report, copy it
verbatim from an existing report rather than rewriting it — it's had a few
rounds of correctness fixes (the `IntersectionObserver` guard, the
`ad-slot` exclusion, the y-axis baseline calculation for x-tick detection)
that are easy to reintroduce bugs into if rewritten from a description.

## SEO setup

Every report (`reports/*.html`) and `index.html` carries:

- `<meta name="viewport">`, `<title>`, `description`, `keywords`
- `<link rel="canonical">` — full `https://coldnew.github.io/stock/...` URL
- `<meta name="robots" content="index, follow">`
- Open Graph (`og:type`, `og:url`, `og:title`, `og:description`) + Twitter
  card (`summary`) — **no `og:image`/`twitter:image` yet**, there's no
  image-generation tooling available to produce one; this is a known,
  intentionally-flagged gap, not an oversight to silently repeat
- `<link rel="sitemap" href="https://coldnew.github.io/stock/sitemap.xml">`
- Google Analytics — **reuses the blog's measurement ID `G-2SXWWHGFPN`**
  (same `gtag.js` snippet as `src/components/BaseHead.astro` in the blog
  repo), meaning report traffic mixes into the same GA4 property as blog
  traffic rather than being tracked separately. That was a deliberate
  choice made once, not re-derived each time — if the user ever wants
  reports tracked separately, that needs an explicit new GA4 property/ID,
  don't assume it.
- `<script type="application/ld+json">` — `Article` schema on reports
  (headline/description/author/dates/mainEntityOfPage), `CollectionPage`
  with a `hasPart` array of `Article` entries on `index.html`
- Favicon — inline SVG data URI (brand-navy square, white uptrend line),
  no external asset file; reuse the same data URI across pages rather than
  designing a new one per report
- `<link rel="preconnect">` to `cdn.jsdelivr.net` and
  `www.googletagmanager.com`
- `font-display: swap;` on both `@font-face` rules
- A real `<h1>` — the report title (`.ticker-name`) is an `<h1>`, not a
  styled `<div>`. Keep it that way; don't regress to a div for a new report.
- `@media (max-width: 640px) { table, .kami-table { display: block;
  overflow-x: auto; white-space: nowrap; } }` so wide financial tables
  scroll instead of breaking mobile layout
- `.breadcrumb` (top, links to `../index.html`) and `.related-report`
  (bottom, links to the *other* report) for internal linking

`sitemap.xml` and `robots.txt` live at the repo root, not per-report.

## Checklist: adding a brand-new report

1. Author the report HTML using an existing report as the template — copy
   its `<style>` block and interactive `<script>` verbatim (see above for
   why), then swap in the new content.
2. Confirm SVG charts follow the gridline/legend authoring convention
   described above, or hover tooltips silently won't work for them.
3. Add all the SEO meta described above (canonical/OG/robots/JSON-LD/GA/
   favicon/preconnect/font-display), a real `<h1>`, and the mobile-table
   CSS.
4. Add `.breadcrumb` (top) and `.related-report` (bottom) — and update the
   *other* existing reports' `.related-report` links if you want them to
   reference the new one too (currently each report links to exactly one
   other report; decide whether that should become a list as the report
   count grows).
5. Add the same top/mid/bottom `.ad-slot` pattern — see the `add-ads`
   skill. As of the site covering OVL/QQQI/BTCI/GPIQ plus `index.html`,
   the user has confirmed ads belong on every page by default; a new
   report should get them without needing to ask again, using the same
   codes already live elsewhere in the site.
6. Add a `.report-card` entry to `index.html`'s `<main class="report-list">`.
7. Add a `<url>` entry to `sitemap.xml` (`<loc>`, `<lastmod>` = today,
   reasonable `<changefreq>`/`<priority>` — see existing entries).
8. Verify with a quick headless smoke test (jsdom, or open in a browser)
   that: the script runs with no console errors, section count matches
   `<h2>` count, `.ad-slot`/`.breadcrumb`/`.related-report` aren't nested
   inside any `.section-body`, and there's exactly one `<h1>`.
